# Lain-VM 规范

> [!QUOTE]
> Lain-IR 能够解释执行（嗨，多稀奇啊）。
> 
> 由 Lain-VM 来在编译期执行 LAINIR。

---

## 0. 架构定位与核心使命

Lain-VM 是编译器内部的专用执行子系统，仅在编译期间运行，不随最终产物发行；目标程序最终直接编译为原生机器码，运行期不存在任何虚拟机环境。

在编译期引入基于能力微内核（seL4 架构风格）的 Lain-VM，旨在确立三项底层契约：

1. **多核 M:N 并发调度**：将元编程的编译期计算解耦为独立的轻量任务，由无状态执行引擎池在宿主多核物理线程间无锁调度；
2. **确定性异步协作**：放弃不可控的宿主多线程共享内存，执行流间仅通过同步端点（Endpoint）进行会合通信，保证任意环境下的编译产物逐字节完全一致（Deterministic Builds）；
3. **宿主绝对安全隔离**：用户在编译期执行的代码（包括宏展开与类型推导）即便发生死循环、非法访存或算术溢出，全部收敛为确定性的异常捕获（Trap），绝对杜绝编译期代码导致编译器本体崩溃（Crash）。

---

## 1. 核心实体与资源模型

Lain-VM 将执行环境解耦为正交的核心实体，各实体职责边界严格分离：

| 实体 | 物理职责 | 明确排除（Non-goals） |
| :--- | :--- | :--- |
| **`Image`** | 静态模块镜像：符号槽位化、地址预烤、代码与静态数据段布局。 | 源代码文本解析、动态执行状态维护。 |
| **`VSpace`** | 物理存储分配；区段划分与映射；有效访问窗口核验；读/写/执行权限仲裁。 | 执行流状态（PC）、调用栈水位。 |
| **`TCB`** | 线程控制块：维持单条执行流的指令计数器（PC）、寄存器槽位、调用栈帧基址；持有 `VSpace` 与 `CSpace` 引用。 | 不直接拥有底层物理内存；不负责物理内存分配。 |
| **`CSpace`** | 宿主服务能力表：受限外部过程的注册、冻结与隐式上下文分发。 | 内存权限判定、业务计算。 |
| **`Endpoint`** | 同步通信会合点（IPC Rendezvous）：执行流间的控制权交接、无锁数据复制与协作式挂起。 | 调度策略制定、高级异步语义解释。 |
| **`Engine`** | 抽象执行引擎（CU + ALU）：纯无状态的单步取指、译码与求值循环。 | 不持有全局状态；不负责内存分配与任务调度。 |
| **`Trap`** | 执行终态记录器：精确捕获失败分类、错误码、过程符号与指令偏移。 | 错误恢复决策、用户诊断信息格式化。 |

---

### 1.1 静态程序映像 (`Image`)

`Image` 是 LAINIR 模块在内存中装载完成的静态只读镜像，所有动态执行依赖的符号在装载时全部消除：

1. **符号槽位化（Slotting）**：过程内部的 SSA 临时绑定（`%name`）在装载期完成全局活性分析，映射为固定尺寸的寄存器槽位下标（`Slot[i]`）；
2. **三段式布局**：镜像划分为只读数据段（`.rodata`）、读写数据段（`.data`）与指令代码段（`.text`）；
3. **地址预烤（Address Baking）**：全局数据对象（`@data`）的引用在装载期直接与物理基址绑定并固化；直接过程调用（`#call @name`）直接解析为目标过程在代码段中的绝对指令偏移。

---

### 1.2 物理地址空间 (`VSpace`)

`VSpace` 是物理内存的唯一仲裁实体，采用区段容量与有效访问窗口双轨模型。

```text
[base, base + accessible)   ──> 当前合法访问窗口（越界直接触发 Trap）
[base, base + capacity)     ──> 底层物理存储硬边界（容量上限）
```

#### 区段类型与接口契约
* **OWNED（自有区段）**：由当前 `VSpace` 在底座物理缓冲中开辟并受容量限制。
* **EXTERNAL（外部切片）**：外部传入的只读或读写内存切片（如宿主传入的语法树内存），直接映射进当前空间，不占用内部底座容量。

```plain
alloc(size)               -> 校验 capacity 剩余 -> 物理内存清零 -> 返回 OWNED 句柄
free(handle)              -> 校验无活借用 -> 归还底层容量 -> 销毁句柄
map_external(ptr, size)   -> 登记为 EXTERNAL 切片 -> 赋予访问权限
unmap_external(handle)    -> 撤销映射关系，不释放外部底层存储
borrow(handle)            -> 增加借用计数（borrow_count++）
end_borrow(handle)        -> 减少借用计数；借用未归零前禁止释放区段
```

#### 物理裸地址 (`#addr`) 语义
* `#addr` 是无类型的纯物理字长数值，不携带对象标识、世代（Generation）或类型元数据；
* 地址的合法性完全由当前执行时 `VSpace` 的 `accessible` 窗口动态判定；
* 过程退出或区段撤销后，该地址访问立即失效；若相同物理地址被重新赋予新区段，新旧裸地址在物理上不可区分；
* 地址与整数之间的转换必须使用 `bitcast` 算子，`bitcast` 仅转换位模式，不授予任何内存访问权限。

---

### 1.3 执行控制块 (`TCB`)

`TCB` 封装单条独立执行流的状态：
* **内部状态**：持有当前指令指针（PC）、活跃调用栈帧指针、栈租约借用句柄与执行终态标志；
* **外部依赖**：持有其绑定的 `VSpace` 与 `CSpace` 的只读引用；
* **隔离性**：多个 `TCB` 可共享同一个 `VSpace`（共享地址空间），但 `TCB` 自身对 LAINIR 保持完全不透明，禁止被解释器内部的代码直接寻址或修改。

---

### 1.4 能力空间 (`CSpace`)

`CSpace` 负责管理执行流调用宿主环境（Host）服务的能力契约。

#### 注册与冻结模型
1. **表项构成**：由外部符号名（`link_name`）、签名、宿主 C 函数指针与**可信上下文指针（`context`）** 构成；
2. **永久冻结（Freeze）**：宿主在初始化阶段通过受控路径注册能力；注册完毕后显式调用 `freeze()`。冻结后禁止新增、修改或删除任何表项，表项内存地址全程稳定；
3. **挂载限制**：`TCB` 仅允许挂载已冻结的能力空间。

#### 隐式上下文注入
宿主外部过程调用的物理签名固定为：
```c
void host_callback(void* context, const uint64_t* args, size_t argc, uint64_t* result);
```
* `context` 指针由 VM 在分派时根据表项自动注入首参数；
* `context` 不进入 `args` 数组，不占用 LAINIR 参数槽，对解释器内部的 LAINIR 代码不可见且不可篡改；LAINIR 参数仅承载业务数据。

---

### 1.5 存储容量与预算边界 (Capacity)

Lain-VM 不设独立的全局账本对象，资源的硬性限制由 `VSpace` 的物理存储底座直接定义：
* **物理底座池化**：宿主在初始化 `VSpace` 时提供固定大小的物理内存缓冲区作为容量上限（`capacity`）；
* **瞬时断定**：区段分配或栈空间扩展仅推进底座内部的偏移指针；当推进量超过 `capacity` 时，分配立即失败并触发容量耗尽 Trap；
* **零开销回滚**：分配失败时底座状态完全不变，无需维护复杂的全局借贷账户。

## 2. 栈模型与执行引擎

### 2.1 栈租约协议 (Stack Lease)

`TCB` 自身不拥有物理存储，其运行时栈空间依据“栈租约”向 `VSpace` 借用：

```text
当前过程激活帧 (Activation Frame)
├── 1. 寄存器槽位堆 (Value Slots) ───── 无地址纯值 (SSA 虚拟寄存器)
│     [ Slot 0: %a   ]
│     [ Slot 1: %b   ]
│
└── 2. 连续物理栈空间 (Stack Memory) ── 可寻址内存 (由 #alloca 推进水位分配)
      [ 物理字节连续区段 ] ─────────── 产生合法 #addr，受 VSpace 窗口约束
```

1. **供给**：调用方在 `VSpace` 内预留一块栈存储区段；
2. **借用**：创建 `TCB` 时传入该租约，区段 `borrow_count` 递增；一份栈租约在同一时刻仅允许绑定一条执行流；
3. **推进**：执行期间，`#alloca` 指令直接推进该区段的 `accessible` 窗口上限；
4. **归还**：`TCB` 销毁或根过程退出时，区段水位归零，借用计数递减；物理存储由供给方负责最终回收。

---

### 2.2 `#alloca` 的生命周期

* **激活帧绑定**：`#alloca` 分配的物理生命周期严格绑定于当前过程激活帧（Procedure Activation）；
* **控制流中立**：进入或退出结构化区域（`#if`、`#loop`、`#switch`）不收回栈内存；仅在过程执行 `#return`、触发 Trap 或 `TCB` 销毁时由激活帧统一回退水位；
* **容量超限**：若循环体内无节制执行 `#alloca` 导致栈水位突破租约的 `capacity` 上限，VM 立即终止执行并触发栈溢出 Trap。

---

### 2.3 抽象执行引擎 (`Engine`)

`Engine` 是无状态的逻辑执行核心，包含控制单元（CU）与算术逻辑单元（ALU）。

#### “借出-执行-回写”工作模型 (Borrow-Run-Flush)
为消除在内存中反复解引用 `TCB` 造成的宿主流水线停顿，`Engine` 遵循如下执行循环：

1. **借出（Borrow）**：执行时间片开始时，`Engine` 将当前 `TCB` 的指令指针（PC）、寄存器槽位首地址（`slots`）与当前帧信息暂存入宿主物理寄存器（C 局部变量）；
2. **调度（Direct Threading）**：基于直接线程化跳转表（`goto *dispatch_table[opcode]`）执行取指、译码与求值，操作数直接在局部槽位数组中读写；
3. **回写（Flush）**：仅在遭遇以下三种边界事件时，`Engine` 将局部寄存器状态同步回写至 `TCB`：
   * 触发执行异常（`Trap`）；
   * 在端点上挂起（`Endpoint` 同步让出）；
   * 过程完成并退出（`#return`）。

## 3. 并发、通信与多核调度

### 3.1 端点同步机制 (`Endpoint`)

`Endpoint` 是 Lain-VM 内部执行流之间同步与控制权转移的一等原语。

#### 会合通信契约 (Rendezvous)
* **无缓冲会合**：`Endpoint` 本身不设数据排队队列。发送方（Sender）与接收方（Receiver）必须同时到达该端点方可完成交接；
* **让出挂起**：若 `TCB_A` 请求向端点传输数据而对端未就绪，`TCB_A` 立即进入 `BLOCKED` 状态并让出 `Engine`；当 `TCB_B` 到达端点时，VM 直接在两者的内存窗口间执行数据复制，并同时将 `TCB_A` 标记为 `READY`；
* **语义中立**：Lain-VM 不内置协程（Coroutines）、异步/等待（Async/Await）或管道（Channels）的高级语义。源语言的所有并发与异步抽象，在 Meta 阶段统一降解为 `TCB` 在指定 `Endpoint` 上的等待与唤醒。

---

### 3.2 M:N 协作式多任务调度

Lain-VM 面向多核编译器设计，原生支持 M:N 调度架构：

```text
宿主物理线程池 (M Threads)       全局就绪队列 (Work Pool)          编译期任务 (N TCBs)
┌──────────────────────┐        ┌──────────────────────┐        ┌──────────────────┐
│ Worker 0 (Engine 0)  │ <───── │ TCB Queue            │ ─────> │ TCB 0 (Macro A)  │
│ Worker 1 (Engine 1)  │ <───── │ (Work-Stealing)      │ ─────> │ TCB 1 (Macro B)  │
│ Worker ...           │        └──────────────────────┘        │ TCB ...          │
└──────────────────────┘                                        └──────────────────┘
```

1. **多核工作窃取**：宿主根据物理 CPU 核心数拉起 $M$ 个工作线程，各线程常驻运行一个无状态的 `Engine` 循环，从共享就绪队列中窃取处于 `READY` 状态的 `TCB` 执行；
2. **执行切片（Fuel Budget）**：每个 `TCB` 分配单次最大可执行步数（Fuel）。切片耗尽仅代表当前调度周期结束，`TCB` 自动回写状态并重回就绪队列末尾，不影响其所持有的配额与生命周期；
3. **确定性构建保证**：所有跨 `TCB` 的通信受到 `Endpoint` 会合时序与有向无环依赖图的强制约束，杜绝不可复现的数据竞争，保证相同源码输入在任意多核配置下生成的 LAINIR 完全等价。

## 4. 异常、终态与语义一致性

### 4.1 确定性 Trap 系统

Lain-VM 彻底废除未定义行为（UB）。一切越权、越界或未定义计算均强制收敛为 `Trap`，向宿主交付结构化错误报告：

| Trap 分类（`VmTrap`） | 触发条件 |
| :--- | :--- |
| **`MemoryOob`** | 访存地址超出当前 `VSpace` 的 `accessible` 窗口边界。 |
| **`Alignment`** | 访存未满足指令显式声明的 `align` 对齐要求。 |
| **`PermViolation`**| 向声明为 `ro` 的只读区段执行写入。 |
| **`ArithDomain`** | 触发除数为零、有符号除法溢出或移位量大于等于位宽。 |
| **`CapDenied`** | 尝试调用 `CSpace` 中未登记或权限受限的外部符号。 |
| **`CapacityExceeded`**| 物理底座分配超限或栈租约空间耗尽。 |
| **`Unreachable`** | 控制流进入带有 `#unreachable` 断言的代码块。 |
| **`State`** | 帧、槽位、切换目标或指令编码处于非法状态。 |
| **`Fuel`** | 单次执行切片的步数配额耗尽。 |
| **`CallDepth`** | 调用深度触碰 `Quota.max_call_depth` 上限。 |
| **`Unimplemented`** | 命中浮点、向量或原子扩展等尚未实现的指令族。 |
| **`StackOverflow`** | 栈租约空间不足以容纳 `#alloca` 申请。 |

`VmTrap` 只给出粗粒度分类，具体成因由 `Subcode` 枚举逐条区分（例如 `Subcode.DivideByZero` 对应 `VmTrap.ArithDomain`，`Subcode.CallArity` 对应 `VmTrap.State`）。

发生 Trap 时，`Engine` 立即终止当前执行循环，记录当前触发指令在 `Image` 中的绝对偏移与所属过程符号，并将 `TCB` 置为 `VmStatus.Dead` 与 `SliceStatus.Trapped` 终态，直接转交编译器宿主生成诊断，绝不波及宿主进程。

---

### 4.2 解释器与 AOT 后端的语义等价性

Lain-VM 与目标平台原生代码生成器（如 AOT 编译后端）必须维持**可观测失败结果的语义等价性**：

* **等价原则**：对于合法输入，解释执行产出的内存状态与 AOT 机器码执行产出的结果必须逐位一致；对于非法输入，两者必须在相同的逻辑语义边界上触发确定性失败；
* **实现解耦**：语义等价**不要求** AOT 机器码在裸汇编指令前冗余插入软件层面的 `VSpace` 窗口比对指令。原生代码应当利用目标 CPU 的硬件内存管理单元（MMU 页保护机制、段对齐与硬件异常）来承接底层安全边界，实现零额外软件开销的物理对齐。
