# 推迟：对象内存能力（原 vm/memcap）

> [!NOTE]
> 这份文档记录一个**没有进入实现**的设计。原来的 seed/include/lain/vm/memcap.h
> 与 seed/src/vm/memcap.c 已删除，内容留在仓库历史里。

## 它原来是什么

受检引用 = 对象身份加偏移，共 16 字节：

- 句柄 8 字节：{ 对象槽 slot, 世代 generation }；
- 偏移 8 字节。

配一张定长对象表（最多 32 个对象）与一张定长能力表（最多 64 条），
世代基数由 lainvm_memcap_init(table, generation_base) 指定，
诊断码 9200-9213（9205 已废弃）。

## 为什么它不进 VM

LAIN-VM 对裸地址的规范（见 [02-lain-vm.md](02-lain-vm.md) 的「裸地址（#addr）语义」）
写死了三件事：

- #addr 是**无类型裸物理地址**，不携带对象身份、世代或目标类型；
- 有效性完全由当前 VSpace 的授权范围与权限位判定；
- 对象级的时间安全（借用检查、世代安全）**属于 Meta 层**，由 Meta 降解为具体物理值。

而 memcap 恰恰把世代编进引用里。把它放进 VM，等于改写 #addr 的定义 ——
那是一份对外契约，代价最大。

它的功能位置正落在文档留下的两个空洞上：CSpace 的「明确不管」栏写着内存权限判定，
VSpace 又明确不带身份与世代。也就是说，它想当的是**带内存对象能力的 CSpace**。

## seL4 不需要世代

memcap 自称要在 CSpace 里管受检引用，对照 seL4（本 VM 的模板）可以看到
seL4 解决同一个问题用的是另外四条路，一条都不需要世代号：

1. 引用是 CSpace 槽索引（seL4_CPtr），而 CSpace 本身在程序寻址不到的地方；
2. CNode_Revoke 一次撤销整个派生子树；
3. 对象被删除或撤销后变 **Zombie**：只要还有 cap 指向就不回收，最后一个 cap
   消失才 finalize 并把内存还给父 untyped。同一块物理内存不可能被复用，
   所以 ABA 问题不存在，也就不需要世代；
4. 用户虚拟地址本身不承诺任何东西，有效性靠页表与 cap 的 rights 位 ——
   这正是本文档「裸地址语义」那一节。

结论：memcap 属于 CHERI 那一脉（引用自带有效性标记），不是 seL4 那一脉。

## 如果它要回来

三条路，按代价排序：

1. **并入 CSpace**（caps.h）作为内存对象能力。要改 #addr 的定义性契约，代价最大。
2. **放进 Meta 层**，作为「Meta 的受检引用在 VM 里的落点」。文档不用改 ——
   文档本来就说对象级安全属于 Meta；而且 meta 已经依赖 vm，不新增依赖边。
3. **不做**。若对象级安全能靠 Meta 的编译期规则保证，运行期的世代检查就是多余的。

9200-9299 号段现已归后端（backend/cbackend）独占，不再属于这里。
