| 类别 | 回答的问题 | 入口 |
| --- | --- | --- |
| 设计理念 | 为什么这样设计，各层负责什么 | [架构](design/architecture.md)、[Meta 与语法树](design/meta.md)、[effect](design/effects.md) |

## 如何处理不一致

代码与测试说明实际行为，规范说明约定行为。两者不一致时，记录缺口并判断应修实现还是修规范。
设计草案和评审建议只有经作者确认后才能修改契约。历史文档不能覆盖现行规范。
实现进度中的数字只对所标明的日期、输入和命令有效。

## 维护约定

1. 除根目录的 README 导航和 AGENTS 入口外，文档只存放于 `docs/`。
2. 设计文档写目的、约束、理由和取舍，不记录任务状态或构建数字。
3. 规范写规则、例子、错误条件和接口。实现缺口链接到进度，不在规范中追加开发日记。
4. 进度写当前状态、证据、未决问题和下一步。完成项更新原条目，详细经过放历史记录。
5. 历史文件保留原路径和日期。旧命令、旧语法不复制进当前指南。
6. 使用具体名称和动词。删除反复强调边界的口号、模拟对话、无依据的“唯一”“全部”“零开销”。
   术语首次出现时解释；用例说明行为，理由说明取舍。加粗只用于需要读者注意的限制。
7. 不用“不是……而是……”组织定义，不用密集感叹或拟人化措辞描述实现。
8. 移动文件时检查链接；修改示例时运行相应工具。新增行为须补验收，文本搜索不能证明行为正确。

本文不建立“代码高于规范”的总排序。实现错误不能自动成为语言规则。
